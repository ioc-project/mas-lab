# Kernel invariants

The kernel is one step function: an event goes in, the product state changes, symbols come out. This page lists the properties that function must keep, the test that holds each one, and a change to the code that makes that test fail (the mutation that kills it). Read it before you change a transition, add a design pattern, or write a plugin that touches a call.

The tests are in `runtime/tests/`: `test_kernel_invariants.py` (every property below that says "all patterns", run for every registered design pattern with a scripted engine), `test_kernel_fidelity.py` (one scenario per defect), `test_kernel_state_writes.py`. The plugin obligations are in `library-standard/tests/test_plugin_contract_conformance.py`.

## Design rule: machines composed by conjunction

Read this before you add a plugin or a field.

- The kernel is a Mealy-style machine: a state, an input event, output intents, and a next state. Every part with behaviour is such a machine: the kernel turn, the session, a governance plugin, the identity layer, a budget.
- Machines compose by conjunction. A step of the whole is allowed only if every machine that cares about it allows it; a machine that does not care stays still (a plugin that does not apply to a call must pass, so the others can decide).
- Machines touch only through a declared interface: named events and shared variables, each with one writer. That interface is the coupling. A plugin contract is the interface specification of its machine, and the conformance test is the check that the machine meets it.
- A safety property of one machine (something bad never happens) survives adding another machine, because conjunction can only allow less. Progress does not: a new machine can refuse forever, so the turn must be shown to finish again (the liveness test).
- State that must survive a restore is registered with the kernel and saved with it. A machine that keeps state of its own outside the checkpoint loses it on restore.

Three kinds of coupling, from cheap to costly:

| Kind | What the machine does | Example in this repository |
| --- | --- | --- |
| Observer | reads kernel events, writes only its own state, never blocks | event emission to observability |
| Veto | may refuse a step; safety stays, progress must be re-checked | a governance deny or a budget cap at egress |
| Data-bearing | its output is a kernel input, or its state must be saved with the kernel | hold state across a pause and a checkpoint; plugin counters across a checkpoint (not saved today, see Known gaps) |

## What the model checker covers and what the tests cover

The tests check the code over the real plugins, engine and driver. A model checker run over a small abstract model of the transition function checks some of the same properties for every interleaving of a few events and calls. The table says where that second kind of check applies and where only the tests can.

| # | Model checker | Tests |
| --- | --- | --- |
| 1 | The chain veto and the approval scope, with two plugins and a single call | Every design pattern, the real chain, parallel calls, `hitl_once_per_turn` |
| 2, 3 | Quiescence and wait-equals-in-flight as state predicates on a small run | The real wait ledger over every pattern and scenario |
| 4, 5, 6 | Pause with a hold kept, one answer per hold, no egress while paused (small, one or two holds) | The code path of the deferred answer, concurrent holds in a real batch, the checkpoint of a pause |
| 7, 8 | A steer and a pause as events that clear or refuse; no egress while paused | The pattern entry points, the egress chokepoint as a second layer |
| 9, 11 | Not expressible (hidden state and a pattern's reading of the ledger are code, not model, structure) | Source scan; pattern scenarios |
| 10 | Turn closes under fairness (a temporal property) | A bounded feed per pattern ends in exactly one outcome |
| 12 | Not expressible until the model's variables are generated from the field list | Round trip of every field after every feed |
| 13, 16 | A boolean blacklist and no tool fields on a model call are not modelled | The per-tool and intent tests |
| 14, 15 | A batch and an egress retry (the retry is a modelled action) | The batch with real engine and queue; the bounded retry |
| 17, 18 | Not expressible (a process-wide store; atomicity is implicit in the model's semantics) | The driver path; exception injection |
| 19, 20 | Not covered (plugin code is outside the model); the veto of a chain of two plugins is | The conformance test and the chain test |

## Plugin types with no conformance test

Governance plugins (egress and ingress) and HITL responders are covered. These registered types have no plugin-contract test yet: `design_pattern` (the kernel invariants above run every pattern, but no test checks that a pattern keeps its per-turn state in a checkpointed place or reads no clock), `agent_comm`, `agent_expose`, `assembler`, `checkpoint_store`, `codec`, `context_manager`, `control_protocol`, `engine_tool_provider`, `eval_metric`, `execute_sandbox`, `hitl_contract`, `layer`, `llm_provider`, `memory`, `observability`, `related_state`, `skill_catalog`, `skill_impl`, `skill_shell`, `skill_tools`, `step`, `summarizer`, `system_plugin`, `tool_provider`, `user_io_contract`, `webserver`. Several have contract tests of their own (for example `checkpoint_store`, `layer`, `control_protocol`), but not a registry-driven conformance test.

## Known gaps

Not fixed here, each with the reason.

- **Pattern state outside the checkpoint.** The deterministic patterns keep participants, round and next index on the plugin instance, not in `q.dp_data`, and the `state_machine` pattern reads `time.monotonic`. `ledger_mark` (which rows of the ledger belong to this turn) is in `q.dp_data` and is restored. Moving the rest needs a decision per pattern, so it is a change of its own.
- **A retry count per turn, not per call.** `gov_retry_count` counts retries across the turn, so a later call in the same turn starts with the count the earlier one left. Per-call counting needs the count on the call (the stable call id makes that possible); it is left until it is wanted.
- **Plugin-held counters.** The kernel's own counters (`gov_retry_count`, the blacklist) are checkpointed. A plugin's counters (the call budget, the policy engine's failure streaks) live in the plugin and are not; a restored run starts them again. A plugin state API is a feature, not a fix.
- **Decision snapshots are taken inside the step.** The governance snapshot is taken at the chokepoint, before the call's effects are applied, because a what-if resume restores to that point and re-runs the decision. Taking it after the step commits would change what a resume restores.
